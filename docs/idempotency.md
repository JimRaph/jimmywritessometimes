# IDEMPOTENCY 

![module 1](/img/idempotency.png)


## The Core Problem (Before “Idempotency” Existed)

The best way to understand Idempotency is by jumping right into real world situation. Imagine you are using a mobile banking app and you press the “Send $10k” button.
You tap the button. Nothing happens for 3 seconds. The screen looks frozen. You think; Maybe I didn't click it properly. So, what do you do? you tap the button again.

Now we ask a very important question: Did you mean to send $10,000 twice? Of course not.

But from the server’s point of view, it just received two identical requests:
1. Send $10k from User A to User B.
2. Send $10k from User A to User B.

The server does not know your intention. It only knows:

1. A request arrived.
2. Then another request arrived.

If the system (mobile banking app you sent the money from) is not designed carefully, the money gets sent twice.
This is the core problem idempotency exists to solve.

________________________________________
## Why This Problem Happens in Software Systems

This problem exists because of how networks and computers behave. Networks are not always reliable. 

When your frontend sends a request:

1.	The request might be delayed
2.	The response might be delayed
3.	The response might be lost
4.	The client might time out  
Etc etc etc

The client does not know if:  
1. The server processed the request  
2.	The request never arrived at the backend  
3.	The request arrived but the response was lost  
4.  The request was successful or not.


So the client often retries the request.
________________________________________
Don’t start thinking the problem is the ‘retries’. Retries are not a bug, but a feature.
Almost all real systems retry automatically:  
•	Browsers  
•	Mobile apps  
•	Payment gateways  
•	APIs  
•	Message queues  

Now here is the danger: A retry might repeat an action that already succeeded.
________________________________________
## The Definition of Idempotency 

I think at this point, you have a grasp of what Idempotency is about. An operation is idempotent if performing it multiple times produces the same result as performing it once. Read that again slowly. I did not say, Idempotency means running once or blocking duplicates. Idempotentcy means no matter how many times an action is repeated, the final state is the same.

Let’s take an example of an Idempotent operation: Set user email to test@gmail.com

If we run it:  
1.	Once -> email is test@gmail.com
2.	Twice -> email is test@gmail.com
3.	Ten times -> email is test@gmail.com  

The final result stays the same!
________________________________________
Now, let’s take a non-Idempotent operation:  Add $10k to balance  

If you run it:  
1.	Once -> +$10k
2.	Twice → +$20k
3.	Ten times → +$100k

Each repetition changes the final state!

It might be tempting to assume that Idempotency is meant to fix bad UI, slow internet, double clicking by user, the answer is NO!
What it fixes is damage caused by repetition. Specifically, it protects against:
1.	Duplicate requests
2.	Network retries
3.	Client timeouts
4.	Accidental resubmissions
5.	Crashes during processing  
You get the idea

It goes without saying that Idempotency is critical for sensitive services such as:
1.	Payments
2.	Order creation
3.	Wallet funding
4.	Subscription billing
5.	Inventory systems
6.	Webhooks
7.	Distributed systems  

If you do not implement it in banking services (or related financial services), well like we say in Nigeria, “see you see prison”😂

## In practice: how is Idempotency handled?

This is where we start talking about something called Idempotency key. An idempotency key is a unique identifier generated by the client and attached to requests, which is used by the server to detect duplicate requests.

The reason it is the client that generates the key instead of server is that, if server did, every retry would create new keys and server couldn’t possibly detect duplicates. Back to this a little later.

One thing is clear at this point. The same request must reuse the same key.

### Implementation
Consider the pseudocode below.   
Let’s consider a crypto situation for this implementation. We would need a wallet and a container holding all processed requests (else how would you know if a request has been processed or not right?)
```Javascript
type Wallet = {
balance: number;
};

const wallet: Wallet = {
  balance: 0,
};

const processedRequests = new Set<string>();

function fundWalletIdempotent(
amount: number,
idempotencyKey: string
) { 
if (processedRequests.has(idempotencyKey)) {
console.log("Duplicate request detected. Ignoring.");
return wallet.balance;
}

wallet.balance += amount;
processedRequests.add(idempotencyKey);
return wallet.balance;
}
```

Let’s fake numbers to test our air-tight defence.

fundWalletIdempotent(5000, "abc123");  balance = 5000  
fundWalletIdempotent(5000, "abc123");  ignored  = still 5000

The client retries, network retries, user clicks twice, devices clicked itself, whatever happens that leads to the request retrying, our airtight defence will protect the system thanks to Idempotency key. This is Idempotency.

Idempotency is not about blocking requests, but making repeated requests safe. Infact, it is not even about the request per se, rather the effect or state that request affects. It is about the state remaining unaffected. 

Again I repeat, Idempotency is not about something running once. It is all about the final state being unaffected irrespectively of the number of times something runs.

If you are building a system that has multiples services, talks over a network, handles money or perform irreversible actions, idempotency is not optional. Again, “see you, see prison”.

## Now we dive deeper

You click “pay”, client generates a key (key_a) and sends the request. You wait but get no feedback, so you click the “pay” button again (key_a is still being used). The server sees key_a when it checks the container holding all processed requests, and doesn’t charge you again.

Hold on… If key is generated client side and sent along with every request why then is it that the second time I click “pay” key_a is still being used? Is it because we didn’t get a feedback from the server? If I did get a response from the server, but still clicked “pay” immediately would the same key be used?

Good questions. The same key is used because client didn’t get a feedback from server, so it can’t tell if the request succeeded. Usually, the retry happens automatically but in our scenario you clicked the ‘pay’ button. This was intentional to explain this part. If server doesn’t provide a response, client doesn’t know if it succeeded, as such, same key is used. If the server did send a response, and you click the “pay” button again, a new key will be used.

For a new key to be used, it means we have to handle the logic for it. The client (browser) doesn’t miraculously know to use a new key, after all, it didn’t create the key to begin with. The other end too, follow same logic. The client doesn’t automatically retry on failure or timeout. We do via code. We include a logic that if a network request fails due to timeout or those 5xx errors, a “retry” block catches the error and resend same request. If it was successful, the success block has to delete key_a.

Let me answer two questions at this point before moving forward:

1. I keep iterating that Idempotency is not about handling ‘double clicks’ etc, you handle things like this by disabling the button. As soon as the user clicks "Send," the button should be disabled (often show a loading spinner). This prevents the user from manually triggering a "second" intent with a new key while the first one is still in flight. Debouncing/Throttling can be used to ignore multiple clicks within a very short window (e.g., 500ms), ensuring only one logical "intent" stays.

2. I mentioned we would come back to addressing why server doesn’t generate the idempotency key. I mean what could possibly go wrong right? Think about the failure point. If the server generates the key, it has to send it back to the client first (else how would you handle retry logic and maintain idempotency?). If the network fails during that initial key exchange request, the client is left in the dark. It wouldn't know if the server generated a key or not, leading back to the original problem of being unsure whether to retry.

So, we have established that we need a client side generated key which is sent along with the request. On error, we retry the same request with the same key. This means we need to store the key in a place that can persist. If we save it in a variable, a page refresh would make us lose the key. So LocalStorage (or any similar storage) should be used. The important criterion is that it should persist a page refresh, browser crash, etc.

### Implementation (Improved)

```Javascript
Async function submitForm(formData){

const idemKey = crypto.randomUUID();
localStorage.setItem(‘form_app_key’, idemKey)

const response = await fetch(‘/api/data/’, {
method: ‘POST’,
header: {‘Content-Type’: ‘application/json’, ‘Idempotency-key’: idemKey}
});

if response is ok: 
remove idemKey from localstorage
perform some other logic.

if response is not ok:
you could inform user a problem happen but request is being retired.
submitForm(formData) -> you should wrap this in a timer (setTimeOut for example) so it has a breathing space before retrying again.
}
```

The code above is an improvement of the first one, but still has issues, most obvious is that the recursion would go on forever. There is nothing to stop it. We will improve on this later.

There are times our browser crashes or server response get lost along the way. In situations like that, there is no way for the client to know the state of that request. This is why I mentioned persistence.

Let’s see how we can handle this.

I can think of two ways to handle something like this:
1. Retry the request on page refresh
2. Inform user to click the button again (to retry the request manually).

In these scenarios, useEffect would be useful. We check on page mount if there is a ‘form_app_key’ in the localstorage, if yes, you could prompt user to try the request again that it was not successful. Or retry automatically. This would depend on the particular situation obviously.

### An improved version of submitForm:

```Javascript
async function submitForm(formData, attempt=1){

const max_attempt = 3; # this is the number of times the request will retry automatically
let idemKey = localStorage.getItem('form_app_key') || crypto.randomUUID(); 
localStorage.setItem('form_app_key', idemKey); 

try{
const response = await fetch();
if(response.ok) remove key and perform other logic
} catch(error){
if attempt >=max_attempt: inform  user you are tired of retrying and request has to be done manually again should user should to continue.
else: setTimeOut(() => submitForm(formData, attempt + 1), 3000)
}
}
```

We can make this better even, instead of retrying every 3s, we could create a delay dynamically so that first time retry is 3s, next is 6s, etc.

```Javascript
const delay = Math.pow(3, attempt) * 1000
setTimeOut(() => submitForm(formData, attempt + 1), delay)
```

So far, we have focused on the client. Time to shift focus to the server.  
The reason we can comfortably do those automatic and manual retry is because we are certain the backend will handle situations where the request was actually successful but the client didn’t know and kept retrying gracefully. 

Server always check the incoming request idempotency key to see if that key exists in its requests container. If yes, it does nothing.

```Javascript
async function airTightDefenceAgainstYourPeaceOfMind(req, res){

const idemKey = req.headers['Idempotency-Key']; 
const userId = req.user.id;

if (!idemKey) { 
return res.status(400).send("Missing Idempotency Key"); 
}

const existingRequest = await db.table('idempotency_keys').find({ key: idemKey, user_id: userId });

if (existingRequest) { 
return res.status(existingRequest.status_code).json(existingRequest.response_body); 
}

try { 
const newApplication = await db.table('applications').create(req.body); 
const successResponse = { message: "Application received", id: newApplication.id }; 

await db.table('idempotency_keys').insert({ key: idemKey, user_id: userId, status_code: 201, response_body: successResponse }); 

return res.status(201).json(successResponse); 
} catch (error) {
return res.status(500).send("internal server Error") } 
}
```

There are few things to note:
1. The container we hold the processed request in can be a database. Using in-memory is not ideal for the same reason we needed localstorage on the client side. Persistence. Using a fast db like redis is perfect here and I recommend it. Fast lookup, and helps with the roundtrip. And Redis TTL helps to clear the container after a while. There is really no need to keep a request idem key for too long.
2. In the case of an error, we don’t save the request idem key into our container.


In the request header on the client side, I used ‘Idempotency-Key’. It is not a must to use the exact name I used. You could use anything as the name but convention is ‘Idempotency-Key’
